# Migration 035: Dynamic Project-Specific Views for QGIS Integration

## Purpose
Creates database functions to dynamically generate project-specific views for QGIS integration with real-time change notifications.

## What It Does

### 1. **create_project_views(project_id)**
Creates two project-specific database views:
- `coordinate_points_project_{id}` - READ-ONLY reference layer
- `land_parcels_project_{id}` - EDITABLE digitization layer

**Features:**
- Automatic project_id filtering
- INSTEAD OF triggers for INSERT/UPDATE/DELETE
- PostgreSQL LISTEN/NOTIFY for real-time updates
- Prevents cross-project data leakage

### 2. **drop_project_views(project_id)**
Cleans up project-specific views, triggers, and functions

### 3. **list_project_views()**
Returns all active project-specific views

## Real-Time Notifications

When parcels are changed in QGIS, the database sends notifications on the `parcel_change` channel:

```json
{
  "action": "INSERT|UPDATE|DELETE",
  "project_id": 123,
  "parcel_id": 456,
  "stand": "Stand A"
}
```

## Usage Example

```sql
-- Create views for project 63
SELECT create_project_views(63);

-- In QGIS: Add PostGIS layers
--   - coordinate_points_project_63 (reference)
--   - land_parcels_project_63 (digitize here)

-- List all project views
SELECT * FROM list_project_views();

-- Drop views when done
SELECT drop_project_views(63);
```

## Security Benefits
- Users only see data for their project
- Cannot accidentally edit other projects' data
- QGIS layer names clearly show project scope
- Database-level isolation (not just application-level)

## Performance
- Views use existing indexes on base tables
- No materialization (always shows current data)
- Minimal overhead for filtering
