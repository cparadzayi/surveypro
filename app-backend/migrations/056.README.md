# Migration 056: Vertex Labeling for Shared Beacons

## Problem Statement

In cadastral surveys, adjacent parcels share common beacons at their boundaries. For example:
- Parcel 1463 has vertices: `1463A`, `1462A`, `1463C`, `1464C`
- These are NOT sequential letters within one parcel
- They represent actual shared beacons between neighboring parcels

Previously, the system auto-generated sequential beacon names (`1463A`, `1463B`, `1463C`, `1463D`), which didn't reflect the actual cadastral topology.

## Solution

Store actual beacon identifiers in the `metadata` JSONB column under a `vertices` array:

```json
{
  "vertices": [
    {"id": "1463A", "y": 18862.52, "x": 2268555.01, "order": 1},
    {"id": "1462A", "y": 18875.14, "x": 2268541.39, "order": 2},
    {"id": "1463C", "y": 18849.88, "x": 2268541.39, "order": 3},
    {"id": "1464C", "y": 18837.26, "x": 2268555.01, "order": 4}
  ],
  "cape_lo_points": [...],  // Existing: for UI-digitized parcels
  "residuals": {...}        // Existing: traverse closure data
}
```

## Database Changes

### 1. Updated Column Comment
Documents the expected structure of `metadata` JSONB field.

### 2. Helper Function: `extract_vertices_from_geometry()`
Extracts vertices from polygon geometry and returns as JSONB array.

**Parameters:**
- `geom_input`: Polygon geometry
- `stand_prefix`: Optional prefix for auto-generating IDs (e.g., "1463" → "1463A", "1463B")

**Returns:** JSONB array of vertex objects

### 3. Update Function: `update_parcel_vertices()`
Updates the `metadata.vertices` array for a parcel.

**Parameters:**
- `parcel_id`: ID of the land parcel
- `vertex_labels`: Optional array of custom vertex IDs

**Behavior:**
- If `vertex_labels` provided: Uses those exact IDs
- If not provided: Auto-generates from `stand` + letters (A, B, C, ...)

## Usage Examples

### Example 1: Auto-generate vertices
```sql
-- Generates: 1463A, 1463B, 1463C, 1463D
SELECT update_parcel_vertices(1463);
```

### Example 2: Set custom vertex labels (shared beacons)
```sql
-- Uses actual shared beacon IDs from QGIS
SELECT update_parcel_vertices(1463, ARRAY['1463A', '1462A', '1463C', '1464C']);
```

### Example 3: Query parcels with vertices
```sql
SELECT 
  stand, 
  metadata->'vertices' as vertices,
  jsonb_array_length(metadata->'vertices') as vertex_count
FROM land_parcels 
WHERE metadata ? 'vertices';
```

### Example 4: Extract specific vertex
```sql
-- Get first vertex of parcel 1463
SELECT 
  stand,
  metadata->'vertices'->0->>'id' as first_vertex_id,
  metadata->'vertices'->0->>'y' as first_vertex_y,
  metadata->'vertices'->0->>'x' as first_vertex_x
FROM land_parcels 
WHERE stand = '1463';
```

## QGIS Workflow Integration

### Step 1: Digitize in QGIS
1. Load coordinate points layer
2. Create polygon layer for parcels
3. Label vertices with actual beacon IDs (e.g., `1463A`, `1462A`)

### Step 2: Store Vertex Labels
When saving parcel from QGIS:
```javascript
// Frontend: Extract vertex labels from QGIS attributes
const vertexLabels = ['1463A', '1462A', '1463C', '1464C'];

// Backend: Update metadata
await updateLandParcel(parcelId, {
  metadata: {
    vertices: vertexLabels.map((id, i) => ({
      id,
      y: coords[i][0],
      x: coords[i][1],
      order: i + 1
    }))
  }
});
```

### Step 3: PDF Generation
Frontend automatically uses `metadata.vertices` when available:
```typescript
// In MapLibreAreaView.vue
if (dbParcel.metadata?.vertices) {
  // Use actual beacon IDs: 1463A, 1462A, 1463C, 1464C
  points = dbParcel.metadata.vertices.map(v => ({
    id: v.id,
    y: v.y,
    x: v.x
  }));
} else {
  // Fallback: Auto-generate 1463A, 1463B, 1463C, 1463D
  points = autoGenerateBeaconNames(stand);
}
```

## Benefits

1. **Accurate Cadastral Representation**: Reflects actual shared beacons between parcels
2. **QGIS Integration**: Preserves vertex labels from QGIS digitization
3. **Backward Compatible**: Falls back to auto-generation if vertices not provided
4. **Flexible**: Supports both UI-digitized and QGIS-digitized parcels
5. **Queryable**: Easy to query and analyze beacon topology

## Migration Safety

- ✅ Non-destructive: Only adds helper functions
- ✅ Backward compatible: Existing parcels continue to work
- ✅ Optional: Vertex labels are optional, auto-generation is fallback
- ✅ No data loss: Existing metadata preserved

## Rollback

```bash
npm run migrate:undo
```

This removes the helper functions and resets the column comment.
